# gruff-data

Community data for GSC tooling, the scripting language of every Call of Duty from CoD1 (2003) to
Black Ops 7 (2025): one dialect profile per game, the sources each fact comes from, and the
measurements behind them. The data is kept apart from any engine so that any tool can use it:
[Gruff](https://github.com/Kenshin9977/gruff) (the GSC toolchain built on it), gscode, GSCLSP or
your own scripts.

The project is not affiliated with Activision, Infinity Ward, Treyarch, Sledgehammer Games or
Raven Software. It contains no game scripts or documentation, and no other game files.

## Layout

| Path | Content |
|---|---|
| `schema/profile.schema.json` | JSON Schema for a dialect profile (after TOML parsing). It doubles as the feature registry: each feature, its value type and a description. |
| `schema/profile.example.toml` | A commented example profile. |
| `schema/hash-package.md` | The hash package format (names for hashed identifiers, read by Gruff's `hash_packages`). The repository ships no package: name lists derived from game files stay local. |
| `profiles/<engine-id>.toml` | One profile per game: keywords, 74 feature flags, unresolved questions. |
| `sources.toml` | Every source a profile may cite, with its licence and how it may be used. |
| `builtins/<game>.toml` | The engine builtin catalogue of a game (functions, methods, arities, parameter types, compiler intrinsics), extracted from the executable by Gruff `tools/re`; where a game ships one executable per mode (T5, T6, IW5, S1, H1), each entry's `modes` (sp, mp, zm) says which executables hold it. Schema: `schema/builtins.schema.json`. |
| `fields/<game>.toml` | The engine field catalogue (T7). Schema: `schema/fields.schema.json`. |
| `events/<game>.toml` | The events the engine notifies (name or hash, receiver, payload), extracted from the executable, with a `[coverage]` table; none is `complete` yet. Schema: `schema/events.schema.json`. |
| `semantics/<game>.toml` | VM behaviours (scheduling, notify, endon, waits, array and struct semantics, name resolution at load) measured by running this project's own conformance scripts in the game's VM, emulated offline from the executable (Gruff `tools/re/vm`): question, answer, golden trace, claims of documents and tools with agree/disagree, static evidence. A behaviour whose form the game's compiler refuses (no such keyword, syntax, literal or builtin) is `unsupported` with the compiler's message, never `pass`; `pass` with a compiler message only when the refusal answers a name-resolution question about a well-formed script. Where the game ships no compiler (T6, and MW3 to IW, whose scripts are bytecode compiled offline), gsc-tool compiles the scripts and its messages stand for the compiler's. Schema: `schema/semantics.schema.json`. |
| `community/<id>/` | Drafts from community corpus reports (`gruff report`, merged by Gruff `tools/re/merge_reports.py`): `builtins.toml` (every entry `confidence = "corpus"`), `events.toml`, `profile.toml` (feature proposals beside the profile's values). Leads for review, read by no tool; provenance per entry. See Gruff `docs/community-reports.md`. |
| `evidence/corpus/<id>.tsv` | Feature counts this project measured on shipped or decompiled scripts: regex probes, then exact parser counts (`parser:` rows) and the keyword-as-name tests (`kwname`, `kwvar`, `kwfunc` rows). They are facts, not scripts. |
| `tools/featcount.py` | The probe that produced `evidence/`. It runs on a local install and stores no file content. `--parser` mode drives the Gruff parser for exact counts. |
| `docs/dialect-matrix.md` | Games × features with ✓ / ✗ / ? and a confidence marker, generated by `docs/gen_matrix.py`. |
| `tools/validate.py` | Checks profiles, builtin, field, event and semantics files against their schema, the source registry and the licence rule (see Validation). |

## Confidence

Every feature value and keyword list carries one of these confidence levels:

- **measured-in-engine**: measured by this project by running its own scripts in the game's
  VM, emulated offline from the executable; the behaviours and their evidence are in
  `semantics/<game>.toml`.
- **verified-on-corpus**: measured by this project on the game's shipped scripts with
  `tools/featcount.py`. The counts are in `evidence/corpus/`. A zero count is weaker evidence: it
  shows the feature is not used, not that the compiler rejects it.
- **documented**: stated by a cited source, such as an official mod-tools document, a tool's
  documentation or a tool's VM tables. A community compiler that *accepts* a construct is not
  evidence that the retail compiler did; such entries are `assumed` unless the tool says otherwise.
- **assumed**: carried by inference from the family or the previous game, or known only from a
  community compiler's superset.

The value `"unknown"` is always allowed. A known blank is better than a guess. An enum feature
also accepts `"n/a"`: the feature does not apply to the game because the construct it is about
cannot occur there (`hash_equality` in a game without hash literals). It is a known answer, with a
confidence and sources like any other value; tools read it as off, never as unknown. When sources
disagree, the entry gets `status = "unresolved"` and the profile gets an `[[unresolved]]` block.
That block lists each claim with its source and the measurement that will settle the question.

`bare_call_resolution` names the order in which a bare call `foo()` reaches the builtins and the
script functions (the schema describes each value). Three were measured in the emulated VMs:
`file-first` (T4, IW3, T5), `builtin-strict` (T6: the builtin even before a function of the same
file) and `namespace-first` (T7 to T9). `builtin-first`, carried by the other games from gscode and
gsc-tool, is measured in none; tools read it as the same file, then the builtins, then the imports,
which is not what gscode means by the name (the builtin before every script function).

## Validation

`tools/validate.py` checks every file of `profiles/`, `builtins/`, `fields/`, `events/` and
`semantics/` against
its JSON Schema in `schema/`, then the rules a schema cannot express:

- profiles: file name = id, every source id exists in `sources.toml`, every licence label follows
  the rule below, every feature an `[[unresolved]]` block names is marked `status = "unresolved"`,
  `hash_equality = "n/a"` only with `hash_string_literal = false`;
- builtin catalogues: file name = game; an entry named from gsc-tool (`name_source` `gsc-tool` or
  `iw5-handler-match`) is `GPL-3.0-only` and no other entry is; every name hashes to its `hash`
  with the file's `hash_family`; no slot listed twice; arities consistent (`-1` only with
  `arity_unknown` or `arity_unchecked`, `measured_args` with `corpus_arity`); intrinsic names
  unique; an entry's `modes` a strict subset of the modes read (`[extraction] modes`) and its
  `mode_args` within its modes; `coverage.complete_modes` among the modes read, with
  `complete = false`; a profile's `opcode_builtins` all present in the catalogue's
  `[[intrinsic]]` list, which is what the tools read (the profile value documents the dialect);
- field catalogues: file name = game, sources known, no duplicate, names hash right;
- event catalogues (`events/<game>.toml`): file name = game, a known `hash_family`, every name
  with a `name_source` and hashing to its `hash`, no event listed twice, no `measured` event
  without a site, and `[coverage]` consistent with the entries (`named`, engine + scripts +
  unexplained = the corpus waits, `complete = true` only with every site resolved and every
  event named);
- semantics files (`semantics/<game>.toml`): file name = game with a profile, behaviour ids
  unique, every passing behaviour with an answer and a trace (or the compiler's message), every
  unsupported one with a reason, every claim's source in `sources.toml`; a profile source
  `vm-<game>-emulation#<id>` names a passing behaviour of `semantics/<game>.toml`, and every
  `measured-in-engine` profile value cites one.

`community/` is not validated: its files are drafts that `merge_reports.py` (Gruff) writes
from community reports, read by no tool, and reviewed by hand before anything moves into the
catalogues above (which then pass the checks).

The schema check needs the `jsonschema` package; a venv keeps it out of the system Python:

```sh
python -m venv .venv                      # ignored by git
.venv/Scripts/pip install jsonschema      # .venv/bin/pip elsewhere
.venv/Scripts/python -I tools/validate.py
```

`--no-schema` runs the repo rules alone.

## Licensing

The repository is **CC0-1.0** by default (see `LICENSE`). Each profile states its file licence,
and an entry can override it with its own `license` field. The rule, enforced by `tools/validate.py`:

1. An entry backed by a measurement of this project (`corpus-*`), or by facts re-derived from an
   official document or a third-party corpus (`usage = "facts-only"` in `sources.toml`), is
   **CC0-1.0**. The project re-derived the fact, and the method is recorded in `sources.toml`, in
   `tools/` and in the entry's note.
2. Otherwise, an entry whose evidence comes only from GPL sources (gscode's documentation, JSON or
   code, or gsc-tool's documentation or tables) is labelled **GPL-3.0-only**. An entry from acts
   alone is labelled **GPL-3.0-only OR MIT**, and an entry from MIT-0 sources alone **MIT-0**. These
   labels stay until the fact is re-derived by this project or the authors dedicate it to CC0.
3. Inference-only entries are CC0-1.0. A source of unknown licence (such as codresearch.dev)
   contributes a bare fact and does not change the label.

The rule is deliberately conservative. A single boolean is unlikely to be protected expression.
Lists and tables, however, may be: EU database right applies to them, and the labels keep
downstream users safe.

**What never enters this repository:** Activision scripts (shipped, decompiled or dumped),
documentation text, syntax files, function descriptions, assets, binaries, or any file copied from
a game or its mod tools. Facts re-derived from such material are allowed: a feature is present or
absent, a keyword exists, a count, a name, an arity. The source and the method must be recorded.
The BO3 mod-tools documents (`GSC_Language.pdf`, `gsc_sublime.zip`) were read locally for the
`t7` profile. Only the facts were kept, and no text was copied. No hash of a game executable
either: a `[meta] dump` names the file an extraction read, never a digest of it, so the data says
which build of the engine it describes without fingerprinting a binary. Which build it was stays
in the extraction's own output, which is not committed.

## Using the data

```sh
python -I tools/validate.py       # schemas (needs `jsonschema`, see Validation), sources, licences
python -I tools/featcount.py t7 "<BO3 install>/share/raw/scripts" > evidence/corpus/t7.tsv
python -I tools/featcount.py --parser <gruff.exe> profiles/t7.toml t7 "<BO3 install>/share/raw/scripts" >> evidence/corpus/t7.tsv
python -I docs/gen_matrix.py      # rewrite docs/dialect-matrix.md from the profiles
```

A consumer should treat `assumed` values as defaults that it may override, `unknown` as
"do not diagnose", and `n/a` as off (the check has nothing to look at). gscode's rule applies here: a missed diagnostic costs less than a false
positive on shipped code.

## Status

Phase 2. 24 profiles of 74 features each. Every game with a local corpus (20 games, 22 corpora)
has been measured with `tools/featcount.py` and its parser mode; `docs/dialect-matrix.md` shows
every value. Eight profiles have the `verified-on-corpus` grade: the clean-source games (iw1, iw2,
iw3, t4, iw4, t5, codol) and t7 (mod tools). The games known only from decompiled bytecode stay
`documented`: a feature they use gets `verified-on-corpus` with a "decompiled" note, but constructs
that acts or gsc-tool rebuild from a bytecode shape (foreach and its key binding, default
parameters, tuples, path-qualified calls, the `function` keyword, the pointer spelling, the
placement of #namespace and #using_animtree, goto/labels) keep their documented value and say why
in the note. s4, iw9 and t10 have no corpus. A zero count never upgrades a value: it is absence of
use, not proof of absence.
